# Security Policy

## Supported Versions

| Version | Supported |
|---|---|
| 1.0.x (current) | ✅ |
| < 1.0 | ❌ |

## Reporting a Vulnerability

**Please do not report security vulnerabilities through public GitHub issues.**

Report security vulnerabilities by email to:

**security@aeglos.systems**

Include as much of the following as possible:

- Type of issue (e.g. authentication bypass, injection, information disclosure, cryptographic weakness)
- Full path of the affected source file(s)
- Location of the vulnerable code (tag, branch, commit, or direct URL)
- Any special configuration required to reproduce the issue
- Step-by-step instructions to reproduce
- Proof-of-concept or exploit code (if available)
- Impact assessment — what an attacker could achieve

The more detail you provide, the faster we can triage and remediate.

## Response Timeline

| Stage | Target |
|---|---|
| Acknowledgement | Within 48 hours |
| Triage and severity assessment | Within 5 business days |
| Remediation and patch | Dependent on severity (see below) |
| Public disclosure | Coordinated with reporter |

### Severity-based remediation targets

| Severity | Target patch timeline |
|---|---|
| Critical (CVSS 9.0+) | 7 days |
| High (CVSS 7.0–8.9) | 14 days |
| Medium (CVSS 4.0–6.9) | 30 days |
| Low (CVSS < 4.0) | 90 days |

We will keep you informed of progress throughout remediation and notify you before any public disclosure.

## Scope

### In scope

- **API authentication** — Bearer token middleware, token handling, auth bypass
- **Encryption module** — AES-256-GCM implementation, key derivation, nonce reuse
- **Flask proxy** — API key exposure through the server-side proxy layer
- **OSINT pipeline** — SSRF via feed URLs, RSS feed content injection
- **Convergence engine** — Prompt injection via ingested intelligence content
- **Ollama integration** — Local LLM interface security
- **Docker configuration** — Container escape, privilege escalation, secrets exposure
- **Dependency vulnerabilities** — CVEs in pinned packages

### Out of scope

- Vulnerabilities in third-party RSS feeds or their content
- Attacks requiring physical access to the host
- Social engineering
- Denial of service against public feed sources
- Issues in unsupported versions
- Reports generated by automated scanners without proof of exploitability

## Security Design Notes

Reviewers should be aware of the following intentional design decisions:

- **Auth is disabled when `AEGLOS_API_KEY` is unset.** This is by design for local/desktop use. It is the operator's responsibility to set a key for any networked deployment.
- **Ollama runs on HTTP (127.0.0.1:11435).** The loopback-only binding is intentional; there is no TLS on a loopback connection.
- **`ssl=False` appears in Ollama/ollama_manager connections only.** These are plain HTTP loopback connections. All external RSS/feed connections use full TLS verification.
- **Classification marking (`UNCLASSIFIED // FOR OFFICIAL USE ONLY`) is a convention label only.** The platform processes publicly available data exclusively.

## Disclosure Policy

We follow coordinated disclosure. Once a fix is available we will:

1. Release a patched version
2. Publish a GitHub Security Advisory
3. Credit the reporter (unless anonymity is requested)

We ask that you give us reasonable time to remediate before any public disclosure, and that you avoid accessing, modifying, or deleting data beyond what is necessary to demonstrate the vulnerability.

## Recognition

We appreciate the security research community's efforts. Responsible disclosures will be acknowledged in the release notes and Security Advisories unless the reporter requests otherwise.
